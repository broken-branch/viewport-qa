# Security

## Current boundary

Scanned pages, links, redirects, subresources, WebSockets, downloads, selectors, filenames, recommendation text, and handoff text are untrusted. Scan only targets you are authorized to access.

Each `open` or `serve` launch binds to `127.0.0.1` on a free port by default and creates a cryptographically random capability. The capability is passed directly to the system browser in a URL fragment, never printed or logged, moves into exact-origin session storage/page memory, and is removed with `history.replaceState`. The unauthenticated `/` response is a generic bootstrap with no report references. Every private route and asset requires an explicit authorization header. Cookies, query parameters, paths, image URLs, referrers, and report files never carry the capability.

The service rejects an unexpected Host, rejects unexpected or null Origin on writes, accepts JSON writes only, bounds request bodies, sends no permissive CORS headers, and applies CSP, frame denial, `nosniff`, no-referrer, and no-store headers. Screenshots are authenticated fetches exposed through revoked Blob URLs. Only validated manifest assets are readable; traversal, symlinks, internal state/settings/identity files, and colocated files are refused. One shared atomic lock-directory protocol admits one review, scan, or baseline writer. Each current generation has a random owner filename, so current-format stale/dead owners and empty crash directories recover without unlinking a replacement. Legacy file locks and legacy `.recovery` artifacts are never changed automatically: stop every older Viewport QA process, manually inspect/remove the artifact, then retry. A second launch can use `--read-only` without becoming a writer.

Restricted scan mode allows local files confined to their selected real directory and loopback targets by default. The public HTTP(S) origin named in the target URL is admitted for that scan; every further redirect, CDN, or resource origin requires an exact `--allow-origin`, and a public target cannot admit a loopback/private origin. Before Chromium starts, Viewport QA resolves every admitted hostname, rejects IANA special-use/private/reserved IPv4 and IPv6 answers (including embedded IPv4 forms), and pins Chromium's resolver to the admitted address for that scan; later DNS address-class changes also fail closed. Requests, redirects, WebSockets, downloads, and service workers fail closed. A permitted-origin download endpoint may receive the initial request before Chromium identifies its response as a download, but that event is canceled and the report transaction never publishes success. Browser contexts are isolated and ephemeral.

Scan publication is transactional: a same-filesystem sibling staging directory is fully closed, hashed, validated, and synced before one rename. Non-empty outputs are refused. Baseline replacement uses an exclusive lock, durable journal, last-good backup, deterministic recovery, and post-commit validation.

Report assets are integrity checked before serving/export. Review writes remain atomic and the service shares the report writer lock with scan/baseline transactions.

The `vqa launch` start page uses the same per-process capability pattern and exact loopback Host/Origin checks. Its unauthenticated root is a generic bootstrap; job state, local-file upload, scan control, recent reports, and the proxied review application are private authenticated routes with bounded JSON bodies and no permissive CORS. The scan browser never receives the controller capability. One identity-owned job may run at a time; report opening and replacement scans are refused until that job finishes or cancellation joins its cleanup. Clicking Scan admits the exact starting origin for that job only; newly observed origins are named for explicit approval, never silently trusted, and approval is discarded with the job. Uploaded local HTML is isolated in a private cache directory and removed after completion, failure, cancellation, replacement, Stop, or idle shutdown, including while approval is pending.
